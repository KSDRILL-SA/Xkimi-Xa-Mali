## Part 2 — Phase 1, what was live (#490–#497)

### The one that mattered most

**L1.** Two admins removing each other concurrently could leave zero admins —
each operation individually legitimate and individually permitted. Worse, two
*different* operations break the same invariant and could not see each other:
revoking a role reads `user_roles`, suspending an account reads `users`.

There is no check that fixes this: under READ COMMITTED each transaction sees its
own delete and not the other's. A transaction-scoped advisory lock, **named for
the invariant rather than either operation**, is what closes it.

**And one the audits missed entirely.** The member app's `setMemberStatus`, at
`POST /api/v1/admin/members/:id/status`, had *no last-admin guard at all* — not a
race, a single request. `status-policy` exists precisely because suspension can
strand the circle the way role revocation can, and the console's copy was given
the rule. This one, one file over, was never given it.

> Sharing a rule only helps the callers that ask it.

### What writing a test found

**L9** made the money-handling contract enforceable instead of commented — and
found four real bugs doing it:

| File | Expression |
|---|---|
| `budget.service` | `mandateAmount - budgetAmount` |
| `report.service` | `totalDue - totalPaid` |
| `insights.service` | `ytd + monthly * remainingMonths` |
| `goal-engagement` | `Math.round(amount * 100) / 100` |

The last is the interesting one: a correct-*looking* copy of `roundZAR` that
rounds **differently** at a `.xx5` boundary. And the third exposed a gap in the
contract itself — it banned `x * n` and offered nothing to write instead, so the
projection routed around it. `multiplyZAR` now exists.

### Two decisions taken on the owner's behalf

Delegated explicitly while the work continued overnight. Both argued from what
the system does today, both reversible, **both should be reviewed**.

- **D1 — the pool may not go negative.** Every debit undoes a specific credit;
  there is no disbursement. `reconcileLedger` was already relying on this in one
  query and saying it nowhere else. What would change it: payouts.
- **D2 — an overpayment stands, and somebody is told.** Rejecting it would make
  the system disagree with the bank about money that physically arrived.
  Crediting forward or refunding automatically moves a member's money with nobody
  deciding to.

### And one correction to our own record

**A2-F30 withdrawn.** We had written that `TRUSTED_PROXY` should be confirmed set
in production "or client IPs are silently absent everywhere". Wrong:
`resolveTrustedProxy` falls back to `vercel` for any absent value, and a test
pins it. That removed an owner action that should never have been on the list.

## Part 3 — Phase 2, the patterns (#498–#502)

Done **before** the gateway work, not after. Every item is a guarantee that
existed on one path and not its sibling — the audits' own thesis. Building a
settlement pipeline on paths that still disagree bakes the disagreement in.

### The largest: a state for "we do not know"

**P6.** The system could say `SUCCESS` or `FAILED` about a money movement and
nothing else. So when a submission timed out — request gone, no answer, the bank
possibly holding the member's money — it had to guess.

**Two schedulers guessed differently, and that is the tell:**

- the debit run called it `FAILED`, and `transaction-retry-failed` collects
  exactly `FAILED` — so a timeout on a debit the bank had accepted was
  **submitted again**;
- the goal plan called anything not `FAILED` collected, and reset `failedRuns` on
  a `PENDING` that had settled nothing — so a plan could submit forever and
  **never pause**.

`UNKNOWN` is deliberately not an inflow: money whose fate nobody knows has not
been received. Nobody resolves one automatically yet, and that is honest rather
than unfinished — the thing that will is the load report, which is Phase 3.

### The claim that was not a claim

**P2.** The comment said *"check what already exists, claim, then submit."* There
was no claim: it read, called the gateway, and inserted afterwards. Two
concurrent requests both read nothing, both submitted, and collided **after** the
member had been charged twice.

Second time this repository has paid for that lesson. **A comment asserting a
safety property is not evidence of one.**

### The one that ran the other way

**P8.** The audit said a resumed plan could produce two `ACTIVE` plans. It cannot
— the partial unique index refuses it. Everywhere else in this work the
application held a rule the database did not; here the database held one the
application had forgotten, and quietly absorbed a case nobody had thought about.
The defect was only that the member got a raw constraint error.

## What is not done, and why

**Phase 3 (the Netcash lifecycle, 8 items) is planned and unscheduled.** It needs
a gateway that does not exist, and enabling one is a business decision — the
DebiCheck application was declined, and the alternatives (another provider, an
aggregator, NASASA) are the owner's call.

One recommendation carried forward: **make load-report polling the primary
settlement mechanism and the webhook an optional accelerant.** The polling
contract is documented and buildable today; the postback contract is not
established, and the current endpoint would reject a genuine Netcash post at the
signature check.

**Phase 4 (certification)** needs credentials.

**D3** — is "last day of the month" a first-class debit day? — blocks G8 and only
G8. It can wait for the gateway decision.
