## Part 1 — the contributions page (#472–#475)

### The tearing, after eight attempts

The page tore on Android through **eight** rounds (#441, #445, #447, #452, #453,
#470, #471, #472). The cause was never on the page.

`<main>` in both app shells carried `animate-fade-in-up` — a **400ms
translateY** — so every page began life inside a compositing layer that was
*moving*. `useCountUp` runs a `requestAnimationFrame` loop calling `setState`
~60×/sec, and four ran at once inside that layer. Blink rasterises tiles it then
never invalidates, so intermediate frames stayed painted.

The owner's screenshot showed **"Make a payment" drawn three times at three
scroll offsets** — three stranded frames of the entry animation, not three cards.

The correlation had been visible the whole time:

| page | calls `useCountUp` | ever tore |
|---|---|---|
| contributions | yes | yes |
| dashboard | yes | yes |
| transactions — *same* gradients, `rounded-3xl`, `shadow-xxm`, `Reveal` | no | **never** |

**Why seven attempts failed.** Each removed cards, shadows, hover lifts and
armed transitions from a page whose visual twin had all of them and was fine.
Round six disabled the count-up — removing *one half of a collision* — so it
looked like a fix, and the wrong lesson was recorded. When the owner asked for
the animation back, the bug came back with it.

Fixed by making the shells fade with **opacity**. Owner confirmed clean on a
real phone.

### The rule, and how it is held

`apps/web/components/contribution/motion.ts`:

> **Nothing containing a live-updating value may have an animating or
> transitioning ancestor.**

- Opacity is safe — no geometry moves
- Transforms belong on **leaves** (icon, arrow), `sm:`-gated including the transition
- Infinite transforms (the dashboard's drifting orbs) are safe as **siblings**, never ancestors
- `transition-all` is banned — it arms `transform` even when nothing moves

Enforced by `shell-entry-animation.test.ts` and
`contributions-motion-policy.test.ts`. Both were **verified against the broken
value first** — a pin that cannot catch the regression is worthless. Writing the
policy test found a real violation: `BudgetGuardModal`'s input used
`transition-all` for a border and ring change.

### The rebuild and styling

Page rebuilt (#473) and restyled to the dashboard's language (#474, #475): hero
panel, `AnimatedStatCard` surfaces, dashboard section headings, drifting orbs.
Order now argues: what you saved → what you owe → your record → where it goes.

## Part 2 — the Fund page, and a mislabelled total (#476, #477)

`getMemberSummary().totalContributed` sums `Contribution.amountPaid` only.
`GoalPayment` is a **separate table**, so a member who paid R6 000 in months and
R2 000 into goals was shown **R6 000** under the words "Total contributed". The
R2 000 appeared in no member-facing total anywhere.

Labels now read "Monthly contributions"; the true total lives on `/dashboard/fund`,
derived from the pool ledger.

**Found while checking the new page could not state anything false:**
`recordOfflineContribution` wrote a `SUCCESS` transaction and **never posted to
the pool ledger**. Since the DebiCheck rejection there is no gateway, so
admin-recorded cash and EFT is *all* the money the Foundation takes in — the one
path carrying every rand was the one not writing to the ledger the Fund page
reads. Nightly reconciliation would have caught it at 05:00; *correct by tomorrow
is not correct*. Now credits immediately, using the reconciler's own
`refType`/`refId` so the nightly pass is a no-op rather than a double credit.

**What nearly shipped false:** the goals table first carried an "All goals" total
under a ledger-derived balance. Those are different measures —
`syncPrimaryGoalProgress` sets the primary fund's `currentAmount` to every
monthly contribution in its window, and `syncAdditionalGoalProgress` adds
admin-recorded `GoalProgress` which never reaches the ledger. Summed, it could
**exceed the fund** while appearing to be part of it. Row removed;
`fund-page-claims.test.ts` now enforces no hard-coded money, that every
`/dashboard/*` link resolves to a real `page.tsx`, and that the "append-only"
claim stays true.

#477 added a **"Reconcile ledger"** button to admin Reports — the reconciler ran
nightly and nothing could reach it. Its own tests caught a real bug: the audit
row recorded `getClientIP(req)`, which on a server-to-server hop is the *admin
app's* address, not the acting admin's.

### The Foundation had never had a backup

**21 runs. 0 successes. 0 artifacts.** The workflow was refusing to run —
correctly — because `BACKUP_AGE_PUBLIC_KEY` was never set, and it will not write
an unencrypted dump of members' ID numbers and bank details.

**Three alarms, all silent:**

1. The workflow's own alert reached only the GitHub Actions tab
2. The app-side dead-man's switch was **blind** — it required `BACKUP_WATCH_TOKEN`, so it raised `BACKUP_WATCH_BLIND` (warning) instead of `BACKUP_NOT_RUNNING` (critical)
3. The go-live preflight never mentioned either variable
4. `backup-selftest` passed daily using its **own** key — green while the real backup failed

Found by reading **workflow history**, not source. `backup.yml` is correct and
well written; only `gh run list` showed it had never succeeded.

### Four faults fixed before one backup could exist

| # | Fault |
|---|---|
| 1 | No encryption key → generated; public half in repo **Variables**, private half offline |
| 2 | No connection string → now **derived from the Neon API** each run, so nobody pastes a credential and it cannot go stale when Neon rotates the password |
| 3 | `pg_dump: server version mismatch` → pgdg client 18 installed fine, but `/usr/bin/pg_dump` is Debian's **pg_wrapper** and the runner ships PG 16. PATH pinned by path with `sort -V` |
| 4 | Branch chosen by **table count** picked the schema-only `preview` → a 126KB dump of an empty schema that **passed the 50KB size guard as a success**. Now chosen by `pg_database_size` |

Fault 4 is the one to remember: *a backup of nothing, arriving with a green tick,
is precisely what that workflow exists to prevent.*

### The branch named `production` was empty

| Branch | Tables | Size |
|---|---|---|
| `production` (was default) | 0 | 7.5 MB |
| `preview` *(schema-only)* | 40 | 10.2 MB |
| **`staging`** | **40** | **12.2 MB** |

The live app ran on `staging` — 97% of project compute, the only branch ever
`Active`. Vercel's Neon integration maps production deployments to the
**default** branch, so the project sat one re-sync away from serving an empty
database.

**Owner set `staging` as the default branch.** Verified three ways: Neon shows
`staging (Default)`, Vercel's Production `DATABASE_URL_UNPOOLED` updated minutes
later, and the backup's "fullest branch is not the default" warning stopped
firing.

### Restore drill — passed, and now automated

```
tables: source=40  restored=40
rows:   source=623 restored=623
```

`restore-drill.yml` dumps the fullest branch, restores into a scratch Neon branch
created from the empty default (so a pass cannot be an artefact of data already
there), compares, and deletes the scratch branch always. Monthly + on demand.
Counts only — no column value is read or printed.

The decrypt half was proved **by hand** with the real private key (header
`PGDMP`, 182,716 bytes). CI can never test that: the key is deliberately offline,
which is what makes storing backups on a public repository defensible.

### ⚠️ The emergency-restore trap

`backup.yml` dumps with PG 18 → archive format **1.16**. The office machine has
PG **16.14**:

```
pg_restore: error: unsupported version (1.16) in file header
```

**The backup is perfect and the machine holding the only key cannot open it.**
Invisible until the night it matters. Fix: Docker (`postgres:18`) or a PG 18
client — `docs/backup-and-restore.md` §8-prod-a.

### Preview branch cleanup

The Vercel–Neon integration does **not** reliably delete preview branches on PR
close. Harmless while previews forked from an empty `production`; not harmless
now they fork from `staging`. `neon-preview-cleanup.yml` deletes `preview/*`
branches whose git branch is gone, skipping the default branch by **id**,
protected branches, and a refusal list.

**Correction on record:** this was first described as a POPIA exposure. That
overstated it — preview deployments sit behind Vercel Authentication (verified:
302 → `vercel.com/login`). It is data minimisation, not breach response.
